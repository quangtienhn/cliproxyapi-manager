# V1.0.0 TO V1.0.1 UPGRADE & MIGRATION VERIFICATION REPORT
> **Historical document (2026-11-11, v1.0.0 era).** Kept for audit trail. In the current v1.0.1 code, SSH key migration and sshd policy refresh run **after** the post-update health check succeeds, so a failed update leaves SSH access untouched. The transcript below predates that ordering change. Priority: `tests/test_upgrade_migration.sh` and `tests/test_update_rollback.sh` are the living evidence.

**Target Workflow:** Safe in-place migration of existing v1.0.0 installations  
**Test Suite:** `tests/test_upgrade_migration.sh`  
**Date:** 2026-11-11  

---

## 1. Upgrade Challenge (P0 Blockers in v1.0.0)
Installations deployed using v1.0.0 with `--setup-tunnel-user` wrote an `authorized_keys` line containing `no-port-forwarding`. If an operator runs `cliproxy-manager update` without an automated authorized_keys migration routine:
- The updated code will still have an unusable SSH tunnel because the user's `authorized_keys` retains the legacy faulty restrictions.
- An automated, non-destructive migration routine was therefore required.

---

## 2. Migration Implementation (`migrate_authorized_keys_file`)
Integrated into `server-installer/lib/installer_core.sh` and orchestrated via `server-installer/update.sh`:
1. **Detection:** Identifies keys matching the tunnel target (`permitopen="127.0.0.1:8320"`) that still have `no-port-forwarding`.
2. **Atomic In-Place Replacement:** Extracts the exact public key payload (`ssh-ed25519 ...`) and rewrites the line using the verified hardened restrictions.
3. **Non-Product Preservation:** Leaves all other SSH keys (such as operator admin keys, NAS backup keys, or CI deployment keys) completely untouched, byte-for-byte.
4. **Idempotency:** A second execution of `update.sh` leaves the file untouched (matching SHA256 checksums).
5. **Rollback Backup:** Creates a `.bak.<timestamp>` file before making changes.
